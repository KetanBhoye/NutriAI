# End-to-end flows (Maestro)

Black-box UI tests that drive the real app on a real emulator/device against a
real backend. They complement `npm test` (vitest) rather than duplicating it:

| | `npm test` | `npm run e2e` |
|---|---|---|
| Covers | payload rules, portion maths, the write queue, dates, cache | screens, navigation, native keyboard/sheet behaviour, the API round trip |
| Runs in | ~250 ms, no device | minutes, needs an emulator and an account |
| Catches | wrong numbers, wrong request bodies | "it saved and then came back", "the sheet jumped" |

Maestro was chosen over Detox for one project-specific reason: `android/` and
`ios/` here are generated by `expo prebuild` and gitignored, so any native test
harness has to be re-applied through a config plugin every time they're
regenerated. Maestro needs no native changes at all.

## Running them

```bash
# once
curl -Ls "https://get.maestro.mobile.dev" | bash

# an emulator (or a connected device) must be running, with the app installed
emulator -avd Medium_Phone_API_36.1 &
adb install -r android/app/build/outputs/apk/release/app-release.apk

npm run e2e:smoke                                   # no account needed
npm run e2e -- -e EMAIL=you@example.com -e PASSWORD=secret
```

Credentials are passed in, never committed. `maestro studio` opens an
inspector against the running app, which is the fastest way to find the right
selector for a new flow.

The same flows run on iOS unchanged (`maestro test` picks whichever
simulator/device is booted) — nothing in them is Android-specific.

## The flows

| Flow | Covers |
|---|---|
| **00-launch** | Boots to sign-in. No account needed, so it runs anywhere — and it catches the worst failures: a bundle that won't load, a native module that crashes on start. |
| **01-sign-in** | Signs in and lands on the tab bar, which only renders behind a valid session. |
| **10-plan-editor-opens-blank** | The editor opens with nothing selected and the saved targets untouched, recalculating only once activity, goal *and* pace are chosen. Has regressed twice. |
| **12-log-weigh-in** | A weigh-in and step count reach the **server** — asserts "Saved for today." and the readout, not merely an encouraging message. |
| **13-log-exercise-session** | A session is priced on the device, and afterwards it is either stored or the refusal is on screen. Never silence. |
| **20-entry-edit-persists** | Edits calories with macros blank, reloads, and the new value survives — the bug that was invisible until the refresh. |
| **21-log-food-and-portion** | Log at a weight, re-portion to half, and both the macros and the server follow. |
| **22-day-navigation** | Yesterday, back again, forward, jump to today — and no navigating into the future. Guards the UTC date bug. |
| **30-food-search-keyboard** | Typing in the food search keeps the sheet on screen and the field focused. |
| **40-trends-and-profile** | The two read-mostly tabs render their charts, tiles and settings; the reminder toggle flips and flips back. |

## Writing more

Prefer asserting **user-visible copy** over `testID`s where the copy is the
promise being made. `10-plan-editor-opens-blank` asserts the sentence "Your
current targets — choose an activity level…" because a test bound to an
internal id would keep passing if that sentence started lying.

Flows that create data must clean up after themselves — they run against a real
account, not a fixture. Use `repeat: while:` for the cleanup so a run that
failed halfway doesn't leave rows for the next one to trip over.

Every authenticated flow starts with `runFlow: ../helpers/ensure-signed-in.yaml`
and must keep doing so. The runner does **not** execute flows in filename
order, so nothing may depend on `01-sign-in` having run first — and each flow
stays runnable on its own.

Four things bit us writing these, all worth knowing before adding a flow:

- **Text selectors are whole-string regexes.** A row reading `200g · 425 kcal`
  does not match `425 kcal`; use `.*425 kcal.*`. Headings with appended hints
  (`How fast?` + the kcal delta) need a trailing `.*` too.
- **Maestro sees through modals.** The screen behind a `Sheet` is in the
  hierarchy, so `tapOn: 'Calories'` hit the macro bar underneath and dismissed
  the sheet. Use a `testID` (`manual-calories`, `food-search`, …) whenever the
  same word appears on both layers.
- **`hideKeyboard` is a Back press on Android**, which closes the sheet you're
  typing into. Tap neutral text inside the sheet instead — it works because the
  sheet sets `keyboardShouldPersistTaps="handled"`.
- **Maestro never scrolls on its own.** Anything below the fold needs
  `scrollUntilVisible`.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This repository contains the code for NutriAI, a calorie tracking application with three main components:
1.  A backend server built with Express.js, providing a RESTful API and an MCP server.
2.  A Vue.js app, now the **admin console**, served at `/app`.
3.  An Expo/React Native app for iOS and Android — which also builds the **consumer PWA** served at `/m`, from the same source.

The backend uses a SQLite database for persistence and can be deployed in various environments, including directly on a Node.js server, in a Docker container, or on platforms like Railway.

## Repository Structure

The repository is a monorepo with the following top-level directories:

*   `src/`: The Express.js backend, API, and MCP server.
*   `web/`: The Vue 3 PWA, which is built into the `public/app/` directory and served by the backend.
*   `mobile/`: The Expo/React Native app for iOS and Android — **and the consumer PWA at `/m`**, which is this same source compiled through react-native-web rather than a second implementation. Same repository, but its own dependencies (npm, not pnpm), test suite and build process. See `mobile/README.md` for setup and architecture, and `mobile/progress.md` for the engineering log — the decisions that look wrong until you know why.
*   `public/`: Built front-ends and static assets. `public/app/` is the Vue admin console, `public/m/` is the mobile app's PWA build (from `mobile/`). Both are committed — nothing on the server runs a bundler.
*   `migrations/`: Contains the database migration scripts.
*   `deploy/`: Contains deployment-related scripts and documentation for different platforms.

## Common Commands

### Backend

*   `pnpm dev`: Starts the backend server in development mode with a file watcher.
*   `pnpm start`: Starts the backend server in production mode.
*   `pnpm test`: Runs the backend test suite.
*   `pnpm test:watch`: Runs the backend tests in watch mode.
*   `pnpm lint:fix`: Lints and fixes the backend code.
*   `pnpm type-check`: Performs a static type check of the backend code.
*   `pnpm db:migrate`: Applies the latest database migrations.

### Frontend (Web)

*   `pnpm web:dev`: Starts the Vite dev server for the Vue.js PWA.
*   `pnpm web:build`: Builds the PWA for production.
*   `pnpm web:type-check`: Performs a static type check of the PWA code.

### Mobile App

*   `cd mobile && npm install`: Installs the dependencies for the mobile app (npm, not pnpm — it has its own lockfile).
*   `cd mobile && npm start`: Starts the Expo development server.
*   `cd mobile && npm test`: Runs the app's unit tests (vitest, no device needed).
*   `cd mobile && npm run e2e`: Runs the end-to-end flows (Maestro, needs a device/emulator).
*   `cd mobile && npx expo run:ios`: Builds and runs the app on an iOS simulator or device.
*   `cd mobile && npx expo run:android`: Builds and runs the app on an Android emulator or device.
*   `cd mobile && npm run web`: Starts the PWA dev server with fast refresh.
*   `cd mobile && npm run web:build`: Builds the PWA into `public/m/`, served by the backend at `/m`. **Rebuild this when a mobile screen changes**, or the web app silently keeps serving the previous build.

## Architecture

### Backend Architecture

The backend is a Node.js application built with Express.js and TypeScript. It follows a layered architecture:

*   **`src/index.ts`**: The main entry point for the application. It initializes the Express server, sets up middleware, and registers the routes.
*   **`src/http/`**: Contains the API routes. `src/http/api.js` registers the main API routes.
*   **`src/auth/`**: Handles authentication, including a custom OAuth 2.0 implementation.
*   **`src/mcp/`**: Implements the Model Context Protocol (MCP) server and its tools.
*   **`src/services/`**: Contains the business logic of the application.
*   **`src/repositories/`**: The data access layer, responsible for interacting with the database.
*   **`src/db/`**: Manages the SQLite database connection, schema, and migrations.

### Frontend Architecture

*   **`web/`**: A Vue.js 3 Progressive Web App (PWA). It is a single-page application that communicates with the backend via the RESTful API.
*   **`mobile/`**: An Expo/React Native application for iOS, Android **and the web**, talking to the same REST API. Reads are cached (`src/cache.ts`), writes a user can't retype go through a durable queue (`src/api/queue.ts`), and the adaptive plan maths is computed server-side in `src/services/goal-progress.ts` so the app and the coach can't disagree. Every tab stays mounted, so a change made on one reaches the others through the small event buses (`src/goalsBus.ts`, `src/entriesBus.ts`) rather than a global store. `ios/` and `android/` there are generated by `expo prebuild` and gitignored — native config belongs in `app.config.ts` or a plugin in `plugins/`. The web build (`/m`) shares all of that; the handful of things a browser genuinely cannot do — the OS cookie jar, native Google Sign-In, per-meal local notifications, Apple Health/Health Connect, APK self-updates, Instagram/Snapchat intents — sit behind `.web.ts` siblings rather than runtime branches. It must be served from this origin: the `ct_sid` cookie is `SameSite=Lax`, so a PWA on another host would never receive it.

## Environment Variables

The application is configured using environment variables. The most important ones are:

*   `PORT`: The port on which the server will run (default: `8787`).
*   `DATABASE_PATH`: The path to the SQLite database file (default: `./data/calorie-tracker.db`).
*   `ADMIN_API_KEY`: The API key for administrative tasks.
*   `ADMIN_EMAIL`: The email for the default admin user.
*   `ADMIN_PASSWORD`: The password for the default admin user.
*   `SESSION_TTL_HOURS`: The time-to-live for user sessions in hours.
*   `BASE_URL`: The public URL of the server.

### The Coach and the other AI features

*   `LLM_PROVIDER`: which provider to use. **Defaults to `anthropic`**, so a
    server with Vertex credentials set but no `LLM_PROVIDER=vertex` reports the
    Coach as not configured (`GET /api/ai/status` → `{"configured": false}`)
    and every AI route 503s — with no error anywhere saying why.
*   `GOOGLE_SERVICE_ACCOUNT_JSON`, `GCP_PROJECT`, `GCP_LOCATION`: Vertex
    credentials. The JSON can be an `authorized_user` ADC file, which is what
    makes local development possible:

    ```bash
    LLM_PROVIDER=vertex LLM_MODEL=gemini-2.5-flash \
      GOOGLE_SERVICE_ACCOUNT_JSON="$(cat ~/.config/gcloud/application_default_credentials.json)" \
      GCP_PROJECT=<your-project> GCP_LOCATION=us-central1 pnpm dev
    ```

    Look for `[vertex] warmed up` at boot. Without these the Coach tab, meal
    ideas, the AI onboarding plan and the weekly report all fall back or
    disable themselves — which is correct behaviour, and easy to mistake for a
    broken client.

Refer to the `README.md` for a complete list of environment variables.

## Deployment

The application can be deployed in several ways:

*   **Directly on a Node.js server**: The `pnpm start` command can be used to run the application in a production environment.
*   **Docker**: A `Dockerfile` is provided to build a Docker image of the application.
*   **Railway**: The application is configured for easy deployment on the Railway platform.

Refer to the `README.md` and the `deploy/` directory for detailed deployment instructions.
